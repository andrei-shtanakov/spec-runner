# Charter — verify-first: объявленная группа принимает файловую цель

`verify_first` доставлен (#367, PR #371–#387): задача, которая проверяет уже
доставленное поведение, начинается живым прогоном объявленной группы, а не
оплаченным RED-зондом. Но словарь объявления остался прежним — **только node
id** (`path::test`). Форма, в которой цель проверки приходит из governance-
конвейера, — файловая (`checked_by … target: tests/test_x.py`). Между
производителем группы и её потребителем стоит ручное расширение файла в
перечень node id, и пока оно не сделано, задача отказывает fail-closed до
первого платного вызова.

Workstream закрывает этот разрыв: **файловая цель становится объявляемой**, с
доказательством не слабее сегодняшнего — «зелёный файл» означает, что из него
собрался непустой набор тестов и каждый его член реально исполнился и прошёл,
а состав, который судили, записан в эвиденцию.

## Контекст и проблема

### Как это устроено сегодня

Объявление группы разбирается `task.py` (`VERIFIES`, `task.py:78`) и хранится
в `Task.verifies` в объявленном порядке. Каждый элемент отдаётся адаптеру
проекта: `PytestAdapter.parse_selector` (`tdd_runners.py:534`) требует `::` и
на всём остальном возвращает отказ. Замерено вызовом адаптера сегодня:

```
>>> adapter_for('pytest').parse_selector('tests/test_verify_first_declaration.py')
SelectorRefusal(code='not_a_node_id',
  message="selector 'tests/test_verify_first_declaration.py' is not a node id (expected 'path::test')")
```

Этот отказ поднимается дважды и в двух разных ролях. На загрузке —
`validate._validate_verify_first_declarations` (`validate.py:620`) выдаёт по
ошибке на каждую дефектную декларацию (нормальный путь: поймать до того, как
хоть один subprocess потратит время). На исполнении — та же нераспарсенная
группа перечислена среди входов `instrument-error`: задача останавливается
fail-closed, `ErrorCode.INFRASTRUCTURE`, exit 2, без единого платного вызова.

Граница объявлена сознательно и записана: `docs/architecture.md:473` — «nothing
else is a selector, including a bare file path. A **file target is not
declarable today** (unlike the `checked_by target: tests/test_x.py` form seen
upstream) … Extending the dictionary to file-level selectors, with proof of
selection at the same strength …, is a deliberately open question left to a
later workstream». То же в `CHANGELOG.md:63`. Этот workstream — тот самый
later.

### Боевой замер: что производит конвейер

Мост `devtools/governance/task_bridge.py` рендерит verify-DT задачей
`**Mode:** verify_first` и собирает строку группы из `checked_target`
сценариев (`task_bridge.py:635`). А `checked_target` — это ровно то, что DSL
behaviour-спеки просит написать: `` `target: <test path>` `` (`ops.py`,
`_AUTHOR_DSL['behaviour-spec']`). То есть производитель по контракту эмитит
путь к файлу, а потребитель по контракту принимает только node id.

Замер по бандлам воркспейса (`*/workstreams/*/spec/15-behaviour-spec.md`,
2026-09-08):

| Всего строк `checked_by` | Несут node id (`::`) | Голая файловая цель |
|---|---|---|
| 190 | 45 (24 %) | **145 (76 %)** |

Три четверти уже написанных целей проверки — в форме, которую spec-runner
отказывается принять. Каждая verify-задача, построенная из такой цели,
доезжает до отказа `not_a_node_id`, и дальше работает человек: руками
разворачивает файл в node id.

### Чего стоит ручное расширение

Замерено на `tests/test_verify_first_declaration.py` (20 тестов) в этом репо:

| | Файловая цель | Ручное расширение в node id |
|---|---|---|
| Длина строки `**Verifies:**` | ~48 символов | **2984 символа** |
| Прогонов на одну живую реверификацию | 1 | 20 |
| Замеренное время группы | **0.36 с** | 6.9–7.3 с (≈20×) |

Множитель не одноразовый: объявленная граница режима — «два живых
реплея на попытку — пол, три — потолок» (CHANGELOG, #367). То есть
20 node id — это 40–60 запусков subprocess за попытку там, где файловая цель
даёт 2–3.

Вторая часть цены — сопровождение. Перечень node id устаревает при любом
переименовании теста внутри файла, и устаревает молча в сторону «меньше
проверили»: старый id просто не соберётся. Файл, в котором тесты добавляют,
надо дописывать в строку руками.

### Что уже есть и не нужно изобретать

- **Байт-лок уже файловый.** `PytestAdapter.claim_paths` возвращает
  `(selector.path,)` (`tdd_runners.py:565`): 20 node id из одного файла
  замораживают ровно один файл. На оси claims тестовая гранулярность
  объявления не покупает ничего — она покупает пер-селекторное
  доказательство.
- **Эвиденция уже двухсоставная.** `live_verify.build_verify_evidence`
  (`live_verify.py:525`) пишет и `group_declared`, и `group_executed`. Место,
  куда положить «во что файловая цель разрешилась», уже существует.
- **Ось доказательства уже трёхмерная.** `classify_verify_outcome` судит по
  `RunOutcome` + `SelectionProof` + `ExecutionProof`; skipped/xfail не
  считается исполнением. Стандарт «молчание — не доказательство» задан, его
  надо распространить на состав файла, а не изобретать заново.
- **Переиспользование эвиденции уже консервативно.** `reusable_verify_evidence`
  (`live_verify.py:551`) сверяет исход, policy-hash, объявленную группу как
  последовательность, происхождение коммита и байт-идентичность дерева.

## Цель

Сделать файловую цель полноправным элементом объявленной группы `**Verifies:**`
— так, чтобы цель проверки, написанная в behaviour-спеке, доезжала до
исполнения без ручного перевода, а сила доказательства зелёного не падала: для
файла доказывается каждый собранный член, а не «прогон в целом вернул 0».

## Пользователи и ожидаемая ценность

- **Автор governance-бандла** пишет `target: tests/test_x.py`, и эта цель
  исполняется как объявлена. Исчезает шаг перевода, на котором сегодня теряются
  76 % целей.
- **Оператор spec-runner** объявляет проверку файла одной строкой вместо трёх
  тысяч символов и не переписывает её при переименовании теста внутри файла.
- **Владелец бюджета и времени прогона** платит за 2–3 запуска на попытку
  вместо 40–60 на той же группе.
- **Читатель эвиденции** видит не только «файл зелёный», но и поимённо, какие
  тесты при этом реально исполнились — то, чего перечень node id даёт по
  построению и что файловая цель обязана дать явно.

## Объём

- **Словарь объявления.** `**Verifies:**` принимает файловую цель наряду с node
  id; смешанная группа (файл + node id в одной декларации) допускается.
- **Разрешение состава.** Файловая цель разрешается в набор членов **против
  того коммита, который судится**, а не против рабочего дерева и не в момент
  парсинга tasks-файла.
- **Доказательство.** Зелёный по файловой цели требует: набор непуст, и каждый
  член доказан исполненным и прошедшим — тем же стандартом
  `SelectionProof`/`ExecutionProof`, что действует сегодня для одного
  селектора.
- **Отказы.** Файл, из которого не собралось ни одного теста (в том числе после
  переименования/удаления), и набор, целиком не исполнившийся, — это
  `instrument_error` с сообщением, называющим файл; отказ на этапе `validate`
  там, где вопрос решается без прогона.
- **Эвиденция.** `group_declared` держит объявленное (файловую цель как
  написана), `group_executed` — разрешённый состав; переиспользование учитывает
  состав, а не только объявленную строку.
- **Три исхода не меняются.** `green` / `test-failure` / `instrument-error` и
  ветвление по ним остаются ровно такими, как их доставил #367.
- **Документация и границы.** Заменить объявленную границу «file target is not
  declarable today» в `docs/architecture.md` и `CHANGELOG.md` описанием
  доставленного контракта; объявить контракт соседям (issue/handoff, не правка
  чужого репо).

## Вне объёма

- **Директории, glob'ы, `-k`- и marker-выражения.** Ровно та ошибка, от которой
  `not_a_node_id` защищает: выражение, матчащее «что-нибудь», не является
  объявленной группой. Файл — конечный, перечислимый и разрешаемый в состав;
  этим он отличается от `-k`.
- **Словарь RED-чекпоинта.** Красный остаётся утверждением про **один** тест;
  файловая цель не становится селектором для `tdd.verify_red`.
- **Политика флейкости.** Не вводится ни усреднение, ни ретраи ни внутри одного
  прогона, ни между реплеями (граница Q-05 из #367 сохраняется).
- **Дедупликация живых реплеев** между собой и с прогоном `post_done_hook` —
  сознательно не трогаем, они судят разные деревья.
- **Семантика green-only ветки**, гейтов и claims: файл и так замораживается
  целиком, менять нечего.
- **Правка соседнего репо** (`devtools`): форму `checked_by` мы не меняем — мы
  делаем её принимаемой. Всё, что требуется от соседа, уходит issue/handoff'ом.

## Продуктовые инварианты

1. **Молчание не читается как доказательство.** Пустой собранный набор и
   набор, ни один член которого не исполнился, — `instrument_error`, никогда не
   `green`.
2. **Сила доказательства не падает.** Файловый зелёный — конъюнкция пер-членных
   доказательств, а не наблюдение за кодом возврата группы.
3. **Группа не угадывается.** Файловая цель — объявление, написанное в
   `**Verifies:**`. Ни имя файла задачи, ни `Traces to`, ни диff, ни прозаическая
   строка чеклиста группой не становятся.
4. **Судится состав того коммита, который судится.** Разрешение членства
   привязано к судимому коммиту; эвиденция называет состав, а не только цель.
5. **Отказ называет причину и остаётся fail-closed.** Ни один неразрешимый или
   недоказуемый случай не проходит как зелёный и не тратит платный вызов.
6. **Обратная совместимость абсолютна.** Группа из node id ведёт себя ровно так
   же, как сегодня; существующая эвиденция остаётся читаемой.

## Критерии приёмки

- `**Verifies:** tests/test_x.py` проходит `spec-runner validate` и доезжает до
  живого прогона: отказ `not_a_node_id` на файловой цели больше не возникает ни
  на одном из двух путей (валидация, исполнение).
- Повторение замера на `tests/test_verify_first_declaration.py`: объявление
  сокращается с 2984 символов до одной файловой цели, а живой прогон группы —
  с 20 запусков (6.9–7.3 с) до одного (≈0.36 с).
- Файл, из которого не собралось тестов, → `instrument_error`, exit 2,
  сообщение называет файл и причину.
- Файл, ни один тест которого не исполнился, → `instrument_error` (тот же
  стандарт, что сегодня для одиночного пропущенного селектора).
- Файл с одним падающим тестом → `test_failure` → немодифицированный TDD-цикл;
  смешанный состав остаётся настоящим падением, не проблемой инструмента.
- Эвиденция зелёного файлового прогона содержит поимённый разрешённый состав, и
  по ней воспроизводимо, какие тесты исполнялись.
- Выборка из 145 замеренных файловых `checked_by`-целей воркспейса объявляется
  без ручного расширения.
- Ни один существующий тест verify-first на node id не меняет поведения.

## Риски и меры

- **Дрейф состава между реплеями.** Файловая цель — запрос, разрешаемый в
  момент прогона; между входным прогоном и пре-мерж реверификацией в файл может
  добавиться тест, а объявленная строка при этом байт-идентична. *Мера:*
  инвариант 4 — состав судится по судимому коммиту и пишется в эвиденцию;
  решение о переиспользовании учитывает состав.
- **Соблазн ослабить доказательство.** «Файл прогнали, exit 0» — самый дешёвый
  и самый неверный ответ; это ровно урок #198, воспроизведённый на другой
  гранулярности. *Мера:* инвариант 2 + приёмка на пустом и неисполнившемся
  наборе.
- **Частично пропущенный файл.** Для одиночного селектора skip сегодня —
  `instrument_error`; для файла skip части членов — обычная жизнь. Молчаливый
  выбор любой из двух трактовок будет неверным для половины проектов. *Мера:*
  вынесено в открытые вопросы, решается явно на design-узле.
- **Крупные файлы.** В этом репо есть файл на 94 теста; групповой потолок
  `VERIFY_GROUP_TIMEOUT_SECONDS` = 1800 с остаётся общим. *Мера:* потолок не
  трогаем — файловая цель уменьшает накладные расходы, а не отменяет ограничение.
- **Рассинхрон с соседом.** Мост в `devtools` уже эмитит форму, которую мы
  примем; но пока контракт не объявлен, сосед может «починить» её у себя,
  переведя цели в node id. *Мера:* объявить контракт issue/handoff'ом до того,
  как это начнут править на той стороне.

## Открытые вопросы

- **Q-A · owner_role: product · blocking: true.** Файл, часть членов которого
  пропущена (skip/xfail), а остальные прошли, — это `green` или
  `instrument_error`? Сегодняшний пер-селекторный стандарт говорит «пропуск —
  не исполнение»; для файла буквальный перенос сделает зелёным почти ничто.
- **Q-B · owner_role: product · blocking: false.** Смешанная группа (файл +
  node id внутри него): дубли — отказ, дедупликация или «объявлено как
  объявлено»?
- **Q-C · owner_role: architects · blocking: true.** Как именно разрешается
  состав и чем доказывается членство — этим владеет адаптер (тот же принцип,
  что и в #198/#220: словарь судит адаптер, не общая эвристика).
- **Q-D · owner_role: architects · blocking: false.** Как переиспользование
  эвиденции (`reusable_verify_evidence`) учитывает разрешённый состав, не теряя
  сегодняшней консервативности.
- **Q-E · owner_role: product · blocking: false.** Нужен ли верхний предел на
  размер разрешённого состава — и является ли его превышение отказом или
  предупреждением.

## Условие завершения

Workstream закончен, когда файловая цель объявляема и доказуема по инвариантам
выше; замер на `tests/test_verify_first_declaration.py` повторён и показывает
заявленное сокращение; замеренные 76 % целей воркспейса объявляются без ручного
расширения; объявленная граница «a file target is not declarable today» снята из
`docs/architecture.md` и `CHANGELOG.md` и заменена описанием контракта; контракт
объявлен соседнему репо через issue/handoff, без правки его файлов.
