# Acceptance — Исполняемый negative control под `Mode: standard` (spec-runner#428)

Стадия `acceptance` бандла
`workstreams/executable-negative-control-under-standard-20260921/`.
Единственный источник критериев приёмки workstream-а: критерии составлены
заново от требований (`10-requirements.md`, FR-01…FR-12, NFR-01…NFR-04) и
сценариев (`15-behaviour-spec.md`, BEH-01…BEH-23); нумерация критериев
чартера сюда не переносится.

Входной набор Must: FR-01…FR-09, NFR-01…NFR-04. Should — FR-10, FR-11;
Could — FR-12 (покрыт условно, см. порог).

Решения владельца 2026-09-21 (AP-12) учтены как вход, а не как предмет
обсуждения: зелёный исход судится доказательством исполнения, красный —
`PROVEN`; бюджет прогонов считается **на попытку**; bump — major;
неприменимый патч — unsatisfied.

Правило чтения: `verification: test` — критерий доказан зелёными
сценариями из `scenarios`; `verification: manual` — прозой названо, что
наблюдает человек; `verification: metric` — прозой назван источник числа,
само число в критерии не зашито.

## Критерии приёмки

### A. Объявление

#### AC-01: Объявление разбирается в два поля, негодное — отвергается · verification: test
traces: [FR-01]
scenarios: [BEH-01, BEH-02, BEH-03]

Наблюдаемый знак: задача с `**Negative-control:** <путь> :: <селектор>`
даёт разобранные путь и селектор раздельно, и ни одно поле не содержит
фрагмента другого; формы без разделителя, с двумя разделителями, с пустым
путём и с пустым селектором дают названный отказ, называющий, чего не
хватает или что неоднозначно; маркер у задачи без waiver'а и waived-задача
без маркера — обе названные ошибки. Задача **без waiver'а и без маркера**
разбирается в `Task`, равный полученному до изменения.

#### AC-02: Негодное объявление стоит ноль платных вызовов · verification: test
traces: [FR-01]
scenarios: [BEH-04]

Наблюдаемый знак: на waived-задаче с отсутствующим или неразбираемым
объявлением счётчик вызовов двойника агента равен нулю, кандидат-коммит не
создан, задача остаётся возобновляемой, и повторный прогон после
исправления объявления доходит до исполнения.

### B. Исполнение

#### AC-03: Чистая половина первой, один селектор на обе · verification: test
traces: [FR-02]
scenarios: [BEH-05, BEH-07]

Наблюдаемый знак: наблюдаемый порядок прогонов — сначала без патча, затем с
патчем; обе половины исполняются против одного кандидат-коммита и с одним и
тем же объявленным селектором; посторонняя правка рабочего дерева после
коммита на вердикт не влияет.

#### AC-04: Негодный стенд стоит один прогон, не два · verification: test
traces: [FR-02, NFR-04]
scenarios: [BEH-06]

Наблюдаемый знак: при чистой половине, не давшей зелёного исхода,
мутированная не запускается — прогонов селектора **не больше одного** (на
раннере, чей preflight читает исходник, их ноль). Норма NFR-04 — два
прогона **на одну попытку** проверки конкретного кандидата; перепроверки
после смены кандидата и инструментальные ретраи считаются отдельно
(AP-12.2).

#### AC-05: Ни одного платного вызова, ни одного оставленного worktree · verification: test
traces: [NFR-01, NFR-03]
scenarios: [BEH-08]

Наблюдаемый знак: `PaidBinaryReached` не поднимается ни на одном пути —
успех, отказ по существу, instrument error, таймаут; после каждого из них
`git worktree list` не содержит каталогов контроля, приватные сборки
удалены.

### C. Вердикты

#### AC-06: Красный засчитывается только по ожидаемой причине · verification: test
traces: [FR-03]
scenarios: [BEH-09]

Наблюдаемый знак: удовлетворён только тот контроль, где патч роняет
**объявленный** тест; патч, роняющий другой тест при зелёном объявленном, и
патч, ломающий сбор, удовлетворённого гейта не дают. Определение красного —
`TESTS_FAILED` + `PROVEN`, без исключений и без второй редакции (AP-12.1).

#### AC-07: Тест, красный без мутанта, — отказ по существу, не поломка стенда · verification: test
traces: [FR-05]
scenarios: [BEH-10]

Наблюдаемый знак: гейт не удовлетворён, контроль не переисполняется ни разу,
сообщение говорит о тесте задачи, а не об инструменте.

#### AC-08: Отсутствующий, неприменимый и нечитаемый патч различаются · verification: test
traces: [FR-05, FR-10]
scenarios: [BEH-11]

Наблюдаемый знак (AP-12.4): патча нет в кандидат-коммите — не удовлетворён,
без переисполнений; `git apply` отверг патч — не удовлетворён, без
переисполнений; файл нечитаем (I/O), git не запустился, подготовка worktree
сорвалась — instrument error с переисполнениями в пределах бюджета. Ни один
из трёх не записан как успешный контроль. Один ненулевой код возврата сам по
себе вердикта не определяет — наблюдается по тому, что сбой запуска git и
отвергнутый патч дают **разные** вердикты.

#### AC-09: Вина стенда не приписывается патчу даже после зелёной чистой половины · verification: test
traces: [FR-04]
scenarios: [BEH-12]

Наблюдаемый знак: таймаут реплея, неподготовленное окружение и недоступный
тулчейн раннера на мутированной половине дают instrument error с
переисполнениями в пределах бюджета, а не «мутант не различил»; ни один из
них не записан как отказ по существу.

#### AC-10: Патч-обусловленный отказ — отказ по существу на обоих измеренных раннерах · verification: test
traces: [FR-04]
scenarios: [BEH-13]

Наблюдаемый знак: на pytest и на ExUnit патч, повреждающий тест-файл так,
что объявленный тест не может быть исполнен, даёт **не удовлетворён** без
переисполнений. Вердикт один, хотя механизм отказа у раннеров разный:
на pytest он приходит прогоном, на ExUnit — preflight'ом. Это обязательный
критерий, а не «желательно бы»: классификация по стадии давала здесь
неверный ответ, и pytest этот дефект не ловит.

### D. Структурная невозможность

#### AC-11: Невыполнимая конфигурация отвергается по имени до платного вызова · verification: test
traces: [FR-09]
scenarios: [BEH-14]

Наблюдаемый знак: `auto_commit: false`, нерезолвящийся адаптер и
композитный `test_command` на waived-задаче дают названный отказ до первого
платного вызова (счётчик двойника агента — ноль), называющий обе стороны
противоречия; ни один не даёт переисполнений и
infrastructure-исхода; после исправления конфигурации прогон проходит.

#### AC-12: Соседи и закрытые задачи не затронуты · verification: test
traces: [FR-09, FR-10, NFR-02]
scenarios: [BEH-15, BEH-23]

Наблюдаемый знак: в проекте с `auto_commit: false`, где есть обычные задачи
и waived-задача со статусом `done` без нового маркера, `validate` не даёт
ошибок из-за закрытой задачи, прогон стартует, обычные задачи исполняются.
Объявленный патч, отсутствующий в рабочем дереве, даёт **предупреждение**, и
`validate` остаётся годным — иначе новая waived-задача не смогла бы
стартовать никогда.

#### AC-13: Нерезолвящийся кандидат-коммит — отказ, а не пропуск гейтов · verification: test
traces: [FR-07]
scenarios: [BEH-16]

Наблюдаемый знак: waived-задача, у которой кандидат-коммит не резолвится, не
получает терминального завершения. Контрольное наблюдение: без этой правки
пустой кандидат заставляет пре-терминальный сайт считать пройденными **все**
гейты.

### E. Свидетельство

#### AC-14: Обе половины записаны и читаются из одного источника · verification: test
traces: [FR-06]
scenarios: [BEH-17, BEH-18]

Наблюдаемый знак: после прогона запись содержит задачу и неймспейс,
кандидат-коммит, селектор, идентификатор патча, исход **каждой** половины,
идентичность окружения и конфигурации, отметку времени; `tdd status
<TASK-ID>` и `--json` показывают одно и то же, значения совпадают; запись
другой задачи или другого неймспейса не читается как своя. Запись
существует и для **неудовлетворённого** контроля.

#### AC-15: Неудача записи не выдаётся за успех · verification: test
traces: [FR-06]
scenarios: [BEH-19]

Наблюдаемый знак: при недоступной записи прогон не падает трейсбеком, и
отсутствие записи не читается позже как «контроль был удовлетворён».

### F. Дормантность, текст, контракт

#### AC-16: Проект без waived-задач не платит за механику · verification: test
traces: [NFR-02]
scenarios: [BEH-20]

Наблюдаемый знак: число git-вызовов, прогонов тестов и открытий state DB на
обычной задаче совпадает с прогоном до изменения; в частности, наличие
механики не заставляет создавать кандидат-коммит там, где он не создавался.

#### AC-17: Текст обязательства описывает новую границу · verification: test
traces: [FR-08]
scenarios: [BEH-21]

Наблюдаемый знак: блок обязательства не содержит «you are the only check»;
говорит, что машина показала различение против приложенного мутанта;
называет предметом ревью соответствие мутанта заявленному свойству; приходит
из КЛАССА — задача, объявившая свои условия, получает тот же текст.

#### AC-18: Контракт синхронизирован, bump объявлен major · verification: manual
traces: [FR-11]
scenarios: []

Наблюдаемый знак: `docs/state-schema.md` описывает новую таблицу; CHANGELOG
несёт запись и объявляет **major** (AP-12.3: новая таблица состояния
подпадает под `AGENTS.md:18`, прецедент минорного v2.36.0 правило не
отменяет); #428 закрыт с evidence; мосту devtools отправлен issue; в
соседнем репозитории не изменено ни одного файла.

#### AC-19: Прогон по требованию не подменяет гейт · verification: test
traces: [FR-12]
scenarios: [BEH-22]

Наблюдаемый знак: напечатанный вердикт совпадает с гейтовым на тех же
входах, и прогон не оставляет свидетельства, которое гейт затем прочитает
как своё.

   **контроля**, а не как повторные оценки гейта: контроль исполняется до
   ревью, гейт читает готовый вердикт. Смысл сценариев BEH-10 и BEH-12

   и допускает резолюцию дизайна.

## Порог приёмки

Workstream объявляется delivered, когда одновременно:

- **Все `verification: test`, кроме AC-10 и AC-19,** зелёные в CI на PR в
  прогоне `uv run pytest tests/ -q -m "not slow"`: AC-01…AC-09, AC-11…AC-17.
- **AC-10** (оба измеренных раннера) зелёный в своём обязательном job —
  контракт ExUnit гоняется отдельной матрицей, и именно там ловится дефект,
  которого pytest не ловит. Красный AC-10 держит workstream не delivered
  так же, как красный из основного прогона.
- **AC-19** (FR-12, Could): либо зелёный в том же прогоне, либо FR-12 явно
  вырезан решением владельца с записью в CHANGELOG-заметке PR — третьего
  состояния («не реализован и не вырезан») порог не допускает.
- **`verification: manual` — по перечислению:** AC-18 подтверждён ревью PR
  и закрытием #428.
- **Ни одна waived-задача класса `characterisation` не может достичь
  терминального завершения без исполненного и записанного контроля** —
  предъявляется AC-11, AC-13, AC-14 вместе; частичная приёмка не
  предусмотрена.

Любой красный критерий из перечисленных, красный обязательный CI-чек или
неприбывшее ревью держат workstream в состоянии «не delivered».

## Вне объёма

Приёмка не проверяет: реализацию FR-12, если она вырезана; поведение на
раннерах вне `ADAPTERS` (они отвергаются AC-11); ретроспективный контроль
закрытых задач TASK-008/009/011 (OUT-03); формулировки сообщений сверх
названной причины.
