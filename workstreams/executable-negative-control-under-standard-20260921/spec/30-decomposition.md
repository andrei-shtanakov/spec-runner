# Decomposition — Исполняемый negative control под `Mode: standard` (spec-runner#428)

Стадия `decomposition` бандла
`workstreams/executable-negative-control-under-standard-20260921/`. Режет
доставку на задачи и объявляет граф зависимостей поверх design
(`20-design.md`) и acceptance (`25-acceptance.md`). Решения владельца
(AP-12) и резолюции design (Q-D — пин `environment_id` + `config_hash`;
Q-G — ограничение «патч не трогает строку объявления» с названной
причиной; Р-1…Р-3) здесь **входные условия и не переоткрываются**.

**Нарезка продиктована владением тестовыми файлами.** Единственный
владелец на файл считается по `checked_by` сценариев, и behaviour-спека
раздала 23 сценария по восьми целям:

| Файл | Сценарии |
|---|---|
| `tests/test_negative_control_declaration.py` | BEH-01, 02, 03 |
| `tests/test_negative_control_gate.py` | BEH-04, 14, 15, 16, 23 |
| `tests/test_negative_control_execution.py` | BEH-05, 06, 07, 08 |
| `tests/test_negative_control_verdicts.py` | BEH-09, 10, 11, 12, 13 |
| `tests/test_negative_control_evidence.py` | BEH-17, 18, 19 |
| `tests/test_negative_control_dormancy.py` | BEH-20 |
| `tests/test_waiver_obligation_text.py` | BEH-21 |
| `tests/test_negative_control_on_demand.py` | BEH-22 |

Два сценария одного файла не могут лежать на разных задачах — иначе у файла
два владельца, и «зелёное» перестаёт быть про одну из них. Отсюда шесть
задач, а не восемь: файлы с одним сценарием подселены к смысловым соседям.

**Ни одна задача не объявляет `tdd_waiver`, и это не совпадение.**
Воркстрим, который строит гейт негативного контроля, сам обязан дойти до
зелёного честным baseline-RED — иначе он доказывает ровно обратное тому,
ради чего написан. Каждая задача ниже — `implement`, и у каждой красный
достижим в её собственных границах; ни одного `type: verify` в графе нет.

**Документация — не отдельная задача.** Под `execution_mode: tdd` задача
без исполняемого сценария не имеет честного red, а единственный
санкционированный класс waiver-а документацию не покрывает. Поэтому
`docs/state-schema.md`, CHANGELOG с **major** (AP-12.3), закрытие #428 и
issue мосту лежат на DT-05 в форме design §4: red и green — поведение,
документация — отдельный коммит той же задачи после green.

## Задачи

#### DT-01: Объявление, статические отказы и отказ до платного вызова · type: implement · owner: dev
scenarios: [BEH-01, BEH-02, BEH-03, BEH-04, BEH-14, BEH-15, BEH-16, BEH-23]
depends_on: []
parallel_group: core

Предмет — design §1 и §4 целиком плюс «нерезолвящийся кандидат» из §5.
Разбор `**Negative-control:** <путь> :: <селектор>` в `task.py` (поля
`negative_control` / `negative_control_error`, деление по ` :: ` ровно один
раз); проверки `validate` с двумя границами — фильтр по статусу (задачи, не
достигшие `done`) и предупреждение вместо ошибки на отсутствующий в рабочем
дереве патч; отказ до платного вызова рядом с точкой 1 claims; предикат
структурной невозможности **одним местом** с четырьмя членами
(`auto_commit: false`, нерезолвящийся адаптер, композитный `test_command`,
неразбираемый селектор); отказ на нерезолвящемся кандидат-коммите в
`post_done_hook`.

Границы. Исполнение контроля, классификация и свидетельство — DT-02…DT-04;
здесь ни одного прогона селектора не делается. Регистрация гейта
появляется в DT-03, поэтому BEH-16 в этой задаче наблюдается через отказ
на waived-пути, а не через реестр.

**Почему первой.** Все её отказы — до платного вызова и до любого реплея;
пока их нет, каждая последующая задача отлаживается на прогонах, которые
не должны были начинаться.

#### DT-02: Общий шов реплея и исполнение обеих половин · type: implement · owner: dev
scenarios: [BEH-05, BEH-06, BEH-07, BEH-08]
depends_on: [DT-01]
parallel_group: core

Предмет — design §2. Выделение `_replay_selector(..., mutate=None,
preflight_only=False) -> ReplayAttempt` с полями `stage`, `refusal_code`,
`outcome`, `proof`, `execution_proven`, `selector_identity`, `detail`,
`environment_id`; переписывание `verify_red` тонкой обёрткой над ним;
применение патча `git apply` внутри worktree; порядок половин (чистая
первой); чтение `selector_identity` внутри каждой половины, пока её дерево
живо.

**Нулевой дрейф RED-пути — предмет собственного красного этой задачи**, и
доказывают его существующие тесты (`test_red_checkpoint.py`,
`test_red_gate.py`, `test_runner_recognition.py`, `test_exunit_adapter.py`),
проходящие **без правок ожиданий**. Правка любого из них — сигнал, что
обёртка изменила поведение, а не только форму.

Границы. Вердиктов задача не выносит: `ReplayAttempt` — факт о прогоне,
классификация в DT-03.

#### DT-03: Классификация, гейт и его потасковая регистрация · type: implement · owner: dev
scenarios: [BEH-09, BEH-10, BEH-11, BEH-12, BEH-13]
depends_on: [DT-02]
parallel_group: core

Предмет — design §3, §4a и §5. Обе таблицы классификации (чистая половина —
три строки, мутированная — восемь, читаются сверху вниз); переспрос разбора
на чистом дереве при `unparseable_test_file`; исполнение контроля **до
платного ревью** с отказом на месте при неудовлетворённом вердикте;
переисполнение при `review_changed_candidate`; перенос вердикта и его SHA в
`facts`; гейт `tdd.negative_control` с молчанием при
`pre_implementation`; потасковая регистрация со **своим**
`borrowed_nc`; переисполнения контроля на instrument error в пределах
`gate_recovery_attempts`.

**Обязателен red на ExUnit** (BEH-13): именно там классификация по стадии
давала неверный ответ, и pytest этот дефект не ловит. Задача не считается
зелёной, пока обязательный ExUnit-job не зелёный — это же условие несёт
порог приёмки (AC-10).

#### DT-04: Durable-свидетельство и обе поверхности · type: implement · owner: dev
scenarios: [BEH-17, BEH-18, BEH-19]
depends_on: [DT-03]
parallel_group: core

Предмет — design §6. Таблица `negative_controls` (задача, неймспейс,
кандидат-коммит, селектор, blob-хэш патча, исход **каждой** половины,
вердикт, `environment_id`, `config_hash` — пин по Q-D, отметка времени);
миграция в существующую БД; чтение через `tdd_status.collect`, то есть один
читатель на текст и `--json`; запись best-effort, чья неудача не роняет
прогон и **не** читается позже как «удовлетворён».

Зависимость от DT-03 — по существу, а не по удобству: записывать нечего,
пока вердикты не выносятся.

#### DT-05: Текст обязательства, дормантность и контракт · type: implement · owner: dev
scenarios: [BEH-20, BEH-21]
depends_on: [DT-04]
parallel_group: tail

Предмет — design §7 плюс проверка дормантности и синхронизация контракта.
Переписывание `WAIVER_REVIEW_OBLIGATIONS["characterisation"]` (уходит «you
are the only check», приходит «машина показала различение против
приложенного мутанта; предмет ревью — соответствие мутанта заявленному
свойству»); измерение дормантности — число git-вызовов, прогонов и открытий
state DB на проекте без waived-задач совпадает с прогоном до изменения.

Отдельным коммитом после green: `docs/state-schema.md` с новой таблицей,
CHANGELOG с записью и объявлением **major** (AP-12.3), закрытие #428 с
evidence, issue мосту devtools (правок в его репо нет).

**Почему дормантность здесь, а не в DT-01.** Измерять «механика ничего не
стоит» имеет смысл, когда механика уже есть целиком: до DT-04 замер
показал бы отсутствие того, что ещё не написано.

#### DT-06: Прогон контроля по требованию · type: implement · owner: dev
scenarios: [BEH-22]
depends_on: [DT-05]
parallel_group: optional

Предмет — FR-12 (Could). Команда прогоняет обе половины и печатает вердикт,
совпадающий с гейтовым; **не** оставляет свидетельства, которое гейт затем
прочитает как своё.

Задача может быть вырезана решением владельца — тогда в
CHANGELOG-заметке PR фиксируется вырезание (порог приёмки третьего
состояния не допускает). Вырезание DT-06 граф не ломает: от неё никто не
зависит.

## Инварианты графа

1. **Каждый сценарий behaviour-спеки лежит ровно на одной задаче.**
   BEH-01, 02, 03, 04, 14, 15, 16, 23 → DT-01; BEH-05, 06, 07, 08 →
   DT-02; BEH-09, 10, 11, 12, 13 → DT-03; BEH-17, 18, 19 → DT-04;
   BEH-20, 21 → DT-05; BEH-22 → DT-06. Дублей и пропусков нет — сверяется механически.
2. **Единственный владелец на тестовый файл.** Восемь файлов, шесть задач;
   ни один файл не упомянут двумя задачами.
3. **Граф — цепь с одной необязательной вершиной.**
   DT-01 → DT-02 → DT-03 → DT-04 → DT-05 → (DT-06). Циклов нет.
4. **Ни одна задача не объявляет `tdd_waiver`.** У каждой честный
   baseline-RED достижим в её границах; `type: verify` не используется,
   потому что ни одно поведение графа не доставлено заранее.
5. **Каждый критерий приёмки закрывается задачей** (перечислением, а не
   диапазоном — диапазон читается человеком и не проверяется машиной):
   AC-01, AC-02, AC-11, AC-12, AC-13 → DT-01; AC-03, AC-04, AC-05 →
   DT-02; AC-06, AC-07, AC-08, AC-09, AC-10 → DT-03; AC-14, AC-15 →
   DT-04; AC-16, AC-17, AC-18 → DT-05; AC-19 → DT-06.
6. **Промежуточные состояния названы.** После DT-02 контроль исполняется,
   но вердиктов не выносит; после DT-03 выносит, но не записывает. Оба
   состояния работоспособны для прогона (ничего не ломают), но
   неполноценны для оператора — поэтому цепь DT-01…DT-04 доставляется
   одним integration-PR, а не порознь.

## Порядок и параллельность

Параллелить нечего: каждая задача потребляет результат предыдущей.
`parallel_group: core` у DT-01…DT-04 означает «одна ветка интеграции», а не
одновременность; `tail` у DT-05 — документация и контракт после
поведения; `optional` у DT-06 — вырезаемая вершина.

Рекомендуемый порядок PR-ов: DT-01…DT-04 одним integration-PR (иначе в
master попадёт состояние, где контроль исполняется без вердиктов), DT-05
вторым, DT-06 третьим или никогда.

## Вне объёма

- Более тонкая нарезка, требующая развести `checked_by` behaviour-спеки по
  большему числу файлов, — это правка upstream'а, а не этого документа.
- Реализация на раннерах вне `ADAPTERS`: они отвергаются DT-01.
- Ретроспективный контроль TASK-008/009/011 (OUT-03).
