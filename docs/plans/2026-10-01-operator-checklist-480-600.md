# Чек-лист оператора: возобновление #480 и песочница #600

Для кого: тимлид или оператор, который принимает решения и нажимает кнопки, но не
обязан знать устройство spec-runner. Агент (Claude Code в этом репо) выполняет
технические шаги сам и останавливается там, где нужен человек; такие места помечены
**[Вы]**. Остальное помечено **[Агент]** — достаточно сказать агенту «делай шаг N».

Состояние на 2026-10-01, spec-runner 4.5.0. Перед началом попросите агента
перепроверить раздел «Где мы сейчас» — состояние могло сдвинуться.

## Что мы делаем и почему так

- **#480** — сохранность состояния исполнения: после сбоя должно восстанавливаться не
  только «какие задачи остались», но и стоимость, захваты файлов, результаты
  неуспешных вызовов. Спецификация (бандл) и план из 14 задач готовы. Платные прогоны
  были остановлены 2026-09-20 после дорогой неудачи первой задачи ($7, 39 минут).
- **#600** — песочница: агент-исполнитель может писать только в рабочее дерево задачи.
  Для macOS она выпущена в 4.3.0, но по умолчанию выключена.

Принятый порядок:
1. довести #480 до контролируемого возобновления;
2. для своих прогонов включить песочницу в строгом режиме (`required`);
3. Linux-песочницу делать отдельным треком;
4. общий дефолт песочницы пока оставить выключенным.

## Что нельзя делать

- Запускать `spec-runner run --all` по этому плану — даже после всех шагов. Только по
  одной задаче, с проверкой результата.
- Запускать любой платный прогон до этапа 4 (то есть пока не закончены этапы 1–3).
- Править узлы бандла или план руками «чтобы прошло»: каждая правка сбрасывает
  одобрение.
- Мержить candidate-PR одобрения не своей учёткой: акт одобрения — это мерж учёткой
  из списка авторизованных одобряющих (ваш основной аккаунт), а не агентом.

## Этап 1. Переодобрить бандл #480

Одобрение двухфазное: агент готовит candidate-PR, **вы его мержите — это и есть
одобрение**, затем агент записывает подпись финализирующим PR-ом. Порядок фиксирован:
узел можно одобрить только когда одобрены те, от которых он зависит.

- [ ] **1.1 [Агент]** Сверить, что бандл в master в том виде, в каком его собираемся
  одобрять (PR с BEH-28 и новым форматом декомпозиции влиты, пины и зависимости
  консистентны), и прислать вам короткое резюме изменений с прошлого одобрения
  (2026-09-20) по каждому из четырёх узлов.
- [ ] **1.2 [Вы]** Прочитать резюме. Если что-то из изменений не устраивает —
  остановиться и сказать агенту; одобрять дальше нельзя.
- [ ] **1.3 [Агент]** Вынести на одобрение `behaviour-spec`:
  `cd ../devtools && uv run python -m governance.task_bridge --run-id durable-continuation-checkpoint-evidence-20260915-4c2a3e --approve-node behaviour-spec`.
  Мост либо создаёт candidate-PR, либо отказывает с причиной, ничего не изменив.
- [ ] **1.4 [Вы]** Открыть candidate-PR, посмотреть дифф узла (что именно одобряете)
  и **смержить своей учёткой**.
- [ ] **1.5 [Агент]** Повторить вызов из 1.3 — мост запишет подпись финализирующим
  PR-ом; агент его смержит (или оставит вам, если мост так настроен) и проверит, что
  узел стал `approved`.
- [ ] **1.6** Повторить 1.3–1.5 для `design`, затем `acceptance`, затем
  `decomposition` (design и acceptance — в любом порядке, decomposition — последним).

Готово, когда: все шесть узлов в статусе `approved`, пины совпадают.

  что `spec-runner preflight` по-прежнему `ready`.

## Этап 3. Песочница для своих прогонов (`required`)

`required` вместо `on`: при `on` прогон без доступной песочницы продолжится без неё,
при `required` — остановится. Для защиты доказательств нужно второе.

- [ ] **3.1 [Агент]** Проверить песочницу на нужном CLI: `spec-runner doctor --cli=claude`
  при `executor_sandbox: required` (вне коммита) — должен быть READY, запись за
  пределы проекта должна отклоняться.
- [ ] **3.2 [Агент]** PR с `executor_sandbox: required` в `spec-runner.config.yaml`.
- [ ] **3.3 [Вы]** Одобрить этот PR (или сказать «мержи»).
